What every number on the screen is, where it comes from, and what it can and cannot tell you.

Nothing in this app is measured by an instrument. There is no tide gauge and no weather station behind any figure. Tides are a harmonic model, weather is a forecast model, and the moon is arithmetic. The one exception is elevation, which is a real terrain measurement.

Data sources

Tide times and heights bundled

The full chain, two steps removed from any authority:

Tide-Forecast.com  (harmonic model, heights above Mean Lower Low Water)
  → scripts/refresh-tides.mjs   (direct fetch, no API token)
    → written to  public/tidedata.json
      → bundled into the build, fetched as a static file
  • Not live. App.jsx fetches a file, not an API. Nothing about tides changes between data refreshes.
  • The times are strings from the scrape, not calculated. A record looks like {"t":"3:21AM","m":0.09,"type":"Low","ts":1785102660}. The app only inserts a space to make 3:21 AM.
  • It expires. The current file covers 22 Aug → 19 Sep 2026. A banner appears in the app once fewer than seven days remain, and node scripts/refresh-tides.mjs refreshes it.
  • This is not INCOIS and not the Indian Naval Hydrographic Office. It is a third-party site's harmonic model, scraped.
  • Two reference lines, your choice. Heights are stored above Chart Datum (Lowest Astronomical Tide — the lowest the water ever falls), which is why no stored height is negative. The tide card offers a switch to Mean Sea Level, the average level, where a tide below average reads negative. Same water either way: only the line you measure from moves, so the difference between any two tides is identical. The app defaults to mean sea level.
    The gap between the two is stations[].mslOffset, written by the scraper as the mean of every extreme in the table (Kannur 0.914 m, Cochin 0.576 m). Officially mean sea level is averaged over a 18.6-year tidal epoch; this approximates it from ~29 days, which spans a full spring/neap cycle and lands within about 0.1 m of published figures. Stored catch-report heights always use Chart Datum regardless of the display setting, so reports stay comparable.
All eight local spots share one tide table. Every spot in tidedata.json has station: "Kannur", so Azhikkal, Mattool, Madayi, Puthiyangadi, Payangadi, Chembalikundu, Payangadi Puzha and Palakodu all show identical tides. Switching spot changes the label, not the numbers. Of the registered stations only Kannur and Cochin have tide tables at all.

Moon phase, illumination, age, zodiac computed

Pure arithmetic in src/lib/moon.js. No network, works offline.

JD    = unix_ms / 86400000 + 2440587.5     (2440587.5 = JD of 1970-01-01)
phase = frac((JD − 2451550.1) / 29.530588853)
        2451550.1 = JD of a known new moon (6 Jan 2000)
        29.530588853 = synodic month, in days
age   = phase × 29.530588853
illum = (1 − cos(2π × phase)) / 2       ← the percentage shown

The check is built in: phase 0 gives (1−cos 0)/2 = 0% (new); phase 0.5 gives (1−cos π)/2 = 100% (full).

The phase name does not come from the illumination. It comes from eight hardcoded thresholds on age: <1.5 New · <6 Waxing Crescent · <9 First Quarter · <13 Waxing Gibbous · <16.5 Full · <20.5 Waning Gibbous · <24 Last Quarter · else Waning Crescent. See Limitations — this is a known defect.

Zodiac is explicitly approximate. Mean longitude 218.316 + 13.176396d plus a single correction term 6.289·sin(M). A real ephemeris uses dozens more, so expect the sign to be wrong near boundaries.

Sunrise, sunset, moonrise, moonset computed

Via suncalc 2.0.1 in src/lib/sunmoon.js, on-device.

  • This build returns degrees, not radians — verified: altitude is −0.349 at sunrise (atmospheric refraction) and 82.99 at solar noon for 11.9°N in July.
  • getMoonTimes scans UTC calendar days while the app runs on IST, so the code probes three UTC days and keeps the events falling inside the Indian day.
  • Some days genuinely have no moonrise or no moonset — about 1 day in 30. The moon rises ~50 min later each day, so occasionally neither event lands inside a single day. The UI shows "none today" rather than an error.

Wind, humidity, temperature, pressure, rain live

api.open-meteo.com — no API key, called directly from the browser (they send access-control-allow-origin: *).

Two models are used, deliberately. Open-Meteo's default best_match was scored against real airport instruments (METAR) at eight Indian airports, querying the model at each instrument's own coordinate so that model error was isolated from grid distance:

ModelHumidity biasHumidity errorWind error
best_match (their default)+4.5 pt7.7 pt4.3 km/h
gfs_seamless−4.4 pt7.7 pt3.4 km/h
ecmwf_ifs025+5.1 pt8.9 pt3.9 km/h
icon_seamless+1.4 pt5.2 pt5.1 km/h

The default was best at neither and pinned Kerala humidity near 99% where instruments read 89%. So the app takes moisture and temperature from ICON and wind from GFS. Measured result: humidity bias +4.5 → +2.0 pt, wind error 4.3 → 3.3 km/h.

The ± figure beside humidity and wind is how far the two models disagree. A large spread means low confidence — it is real uncertainty, not decoration.

The grid is 5–8 km wide. Requests snap to the nearest model grid point, which around Kannur means Azhikkal, Mattool and Puthiyangadi can land in the same cell and return byte-identical wind and humidity. No weather product resolves spots 3–8 km apart; the real difference between them is smaller than every model's error bar.

Waves and swell period live

marine-api.open-meteo.com. Two uses: current conditions, and 30 days of recorded daily history for the "Range here" block (wave_height_max, wave_period_max). Those historical figures are recorded, not forecast.

Wave rows are hidden at the river spots. The marine API has no concept of a riverbank — asked for waves at a river it snaps to the nearest ocean cell and returns the swell there. Measured: Payangadi Puzha 1.32 m / 9.95 s from a point 4.7 km offshore; Chembalikundu 1.10 m / 9.75 s from 4.0 km offshore. Those numbers are true for the open sea and meaningless on a river, so they are suppressed. The inland list is src/lib/places.js. Tides are not suppressed — Kerala's backwaters and river mouths are genuinely tidal.

Altitude live

The only figure in the app backed by a real measurement: a Copernicus DEM lookup at your exact coordinate (~90 m resolution), returned by Open-Meteo. It varies over ~100 m of ground, unlike the weather values. A reading of 0 m means the DEM cell is water.

Your location user

navigator.geolocation, from the device. Used to find the nearest station by great-circle distance (haversine, R = 6371 km). Tides then come from that station, but weather uses your actual coordinates, not the station's.

Dates, weekday and month names computed

From the browser's own ICU tables via toLocaleDateString with en-IN or ml-IN — not from any file. Timezone is hardcoded Asia/Kolkata.

Values that are calculated, not fetched

These look like data but are not. Knowing which is which matters when judging accuracy.

The "Now" tide level

This number appears nowhere in the source data. It is interpolated between the two scraped extremes bracketing the current moment:

f      = (now − previous.ts) / (next.ts − previous.ts)
weight = (1 − cos(π × f)) / 2          ← half-cosine S-curve
level  = previous.m + (next.m − previous.m) × weight

A cosine is used because a tide between two turning points is roughly sinusoidal: zero slope at each extreme, steepest at mid-tide. It is the smooth equivalent of the sailor's rule of twelfths — but it is interpolation between two scraped points, not a harmonic model.

"Rising" / "Falling"

Simply next.m > previous.m. A direction only — no rate is ever calculated. Nothing in the app gives you metres per hour.

The animated water level

clamp((level − min) / (max − min) × 100, 8, 96) across the whole loaded table. Because it is clamped to 8–96%, the fill height is not a linear reading — it is decorative, so there is always visible water. Read the number, not the picture.

Four tide tiles per day

Some days genuinely have only three tides — the semidiurnal cycle is ~12 h 25 m, so the pattern drifts ~50 min later each day and roughly every fortnight the fourth extreme slips past midnight. Rather than show a broken-looking row, the forecast borrows the next day's opening tide and marks it "next day". Nothing is invented: every tile is a real tide, labelled with the day it actually falls on. Filters ("High only" / "Low only") are never padded.

Architecture

Browser (React + Vite, PWA)

   ├─ public/tidedata.json ................ tides (static, bundled)
   ├─ api.open-meteo.com .................. weather      (direct, no key)
   ├─ marine-api.open-meteo.com ........... waves        (direct, no key)
   │
   └─ /api/*  →  Netlify Functions (server-side secrets)
                    ├─ catch-report .... insert a report  → Supabase
                    ├─ catch-stats ..... read aggregates  → Supabase
                    ├─ admin ........... CRUD, Basic auth → Supabase
                    ├─ weather ......... optional Google Weather provider
                    ├─ push-config ..... hand the browser the VAPID public key
                    ├─ push-subscribe .. store a device subscription → Supabase
                    └─ push-send ....... scheduled every 5 min, sends push

Why functions exist at all: the Supabase service_role key bypasses Row Level Security, so it can never be in the browser; the browser cannot read its own public IP, which the report schema records; validation in the browser is bypassable; and a scheduled sender must run with no browser open.

Alerts

The rule

OptionValues
Lead timeat the tide, 15, 30, 45 min, 1, 1.5, 2, 3, 4, 5, 6 hours
Which tideLow · High · Any
Conditions (optional)tide height · wind speed · wind gust · wave height · humidity, each below or above a value

Conditions are checked at the tide, not now

A rule like "wind under 15 km/h" asked at 9 pm about a 4 am low tide is a question about 4 am. Current conditions cannot answer it. The app fetches the hourly forecast and reads the values at the tide's own timestamp. The difference is real — in one measured case wind was 18 km/h at the 4:52 am low but 12.2 km/h at the 11:26 pm high.

If a condition cannot be evaluated (no forecast for that field) it fails rather than passing silently, so a rule you set is never quietly bypassed. When a rule blocks an alert, the card says which condition failed and by how much.

Why a timer alone is not enough

A single setTimeout is not a promise about the wall clock. A hidden tab is throttled to roughly one wake per minute, and a sleeping phone freezes the page entirely — on wake the timer resumes counting the remaining delay from that instant instead of catching up. Measured on a fake clock, a 6-hour warning with a 7-hour sleep in the middle fired 5.5 hours late. The scheduler therefore re-derives the countdown from Date.now() on every wake, in ticks capped at 15 s, plus an immediate check when the page becomes visible.

Alerts with the app closed

Even a correct timer cannot run when the app is closed — Android freezes a backgrounded tab within minutes and then discards it. Reaching a closed browser needs a server, so the rule is registered with one: push-send runs every 5 minutes, finds each device's due tide, re-checks the conditions against the forecast at that tide, and sends an encrypted Web Push that the service worker displays with no page running. Exactly one route is ever armed, so an open device cannot also raise its own duplicate.

Android requires the service worker. new Notification() throws "Illegal constructor" on Android Chrome — it is forbidden there, though it works on desktop. All notifications go through ServiceWorkerRegistration.showNotification(), with the constructor kept only as a desktop fallback for when no worker is registered.

Daily summary

Today's moon phase and every tide, at a chosen time, for a chosen place. Time is stored as HH:MM in IST wall-clock — India has no daylight saving, so "05:30" means the same instant every day and never drifts. With "deliver even when closed" off, the time never leaves the phone: the server stores daily_time = NULL and a timer in the page delivers it. Privacy is enforced by what is written, not by hiding a field.

Catch reports

Fields: what was caught (fish / crab / other + free text), quantity in kg via slider or the Good = 5 / Normal = 1 / Bad = 0 presets, and optional notes.

Every report carries a snapshot of the conditions at the moment of submission — tide state and height, next extreme, moon phase and illumination, wind, humidity, elevation and wave height. Stored per row rather than joined later, because the forecast for a past moment cannot be reconstructed. Values are stored in canonical English (rising/falling, high/low, English moon phase) regardless of UI language, so Malayalam reports do not fragment the dataset.

Two identifiers, and both are needed:

  • device_id — a random UUID generated once and kept in localStorage. Stable per phone.
  • ip — read server-side from the Netlify edge, because a page cannot read its own public IP.

Group by device_id for per-user analysis, never by ip: mobile carriers put many users behind one address (CGNAT) and rotate them, so IP both merges different people and splits the same one over time.

Analysis dashboard

  • Line chart — one point per report, catch weight against time. Y starts at zero deliberately: with weights the distance from zero is the quantity, so a truncated axis would exaggerate every difference.
  • Tap a point (or a table row) to open that report with every condition recorded at the time.
  • Table view — all reports, 13 columns, newest first.
  • "When the catch is biggest" — conditions ranked by average catch.
A hard sample-size floor of 5. A group with fewer than 5 reports is dimmed, labelled "too few", and excluded from "best" and "worst" — even when it has the highest average. Tested adversarially: a 2-report group averaging 9.7 kg was correctly excluded in favour of a 10-report group averaging 6.6 kg. With nothing above the floor the dashboard says so rather than presenting noise as a finding.

Charts are hand-rolled SVG. recharts was rejected: 7.1 MB unpacked and 11 dependencies (including Redux) for three charts, against a total bundle of ~200 KB.

Magnitude is carried by bar length and sort order, never colour. The obvious green-good/orange-bad split fails colour-vision checks — those two separate by only ΔE 6.7 under deuteranopia, which affects roughly 1 in 12 men.

Admin panel

At /admin. View, create, edit and delete reports — single rows or a selected batch — in a table or chart view.

The login form is not the security boundary. Credentials are verified server-side on every request; the React form only collects them. A password checked in the browser would be readable in the public bundle, and the API would still be open to curl. If ADMIN_USER or ADMIN_PASSWORD is unset the API returns 503 for everything — there is deliberately no default password, because a default in a public repo is the same as no password.
  • Comparison is timing-safe: both sides are SHA-256'd first so the digests are equal length (a length mismatch would itself leak information), and username and password are both compared regardless of whether the first matched, so response time does not reveal which half was wrong.
  • Column allowlist on writes: id, created_at and ip cannot be forged or renumbered. A request touching only those returns nothing to update.
  • catch_type and quantity_kg are re-validated after defaults are applied.
  • No rate limiting — Netlify Functions are stateless. A weak password is the entire exposure.

Environment variables are baked into a deploy. Setting one in the dashboard does nothing to the deploy already running. Always redeploy afterwards — this is the single most common cause of "not configured" errors.

Known limitations

  1. The moon phase name can contradict "Next full". The name comes from crude age bands (Full = age 13.0–16.5 days) while the date comes from an actual phase search. True full moon is at age 14.765, so the band is −1.77/+1.73 days wide and the card can read "Full Moon" while saying the next full moon is two days away. Fix: derive the name from phase proximity instead of bands.
  2. Tide data expires. The bundled file covers 22 Aug → 19 Sep 2026. Re-run the scraper before it lapses.
  3. All local spots share one tide table — switching spot changes only the label.
  4. Weather cannot resolve neighbouring spots. 5–8 km grid; nearby places legitimately read identically.
  5. No rate limiting anywhere. Catch reports are public and unauthenticated; anyone can submit and pollute the averages. The admin endpoint has no lockout.
  6. Malayalam is unreviewed. Place names, zodiac and the original tide terms were pre-existing; everything else was written during development and has not been checked by a native speaker.
  7. No "not for navigation" notice is displayed. It was removed from the header and footer at the owner's request. Heights remain approximate near shore.

Operations

Running locally

npm run dev       # Vite only, port 5173 — NO /api/* functions
npm run dev:api   # netlify dev, port 8888 — everything works

Use 8888. Catch reports, admin and push all fail on 5173 because the functions do not exist there.

Refreshing tide data

Re-run the Apify scraper and regenerate public/tidedata.json. See the README.

Offline behaviour

A service worker precaches the app shell and the tide table. With no signal, tides, moon, sun/moon and the 7-day forecast all still work; live weather fails and says so. Verified with the network fully disconnected. The worker discovers its own hashed asset filenames by parsing index.html at install, because the build hashes them and they cannot be listed in advance.
